# GitHub PR 数据提取策略分析

## 1. 概述 (Overview)

### 目标
为了提升 AI 生成 PR 描述的质量，我们需要在生成描述前，获取当前 Pull Request 的**文件变更列表 (File Changes)** 和 **提交历史 (Commits)** 作为关键上下文。

### 核心挑战
主要的技术挑战在于，用户触发"AI 生成"功能时所在的页面（通常是 PR 的主对话页面），与我们所需数据所在的页面（`Files changed` 和 `Commits` 标签页）并不相同。我们必须设计一种方案，在后台获取这些跨页面的数据，且整个过程不能干扰用户的正常操作流程。

## 2. 方案分析：前端数据获取 (Analysis: Frontend Data Fetching)

### 推荐方案：后台 `fetch` 与 `DOMParser`
这是我们推荐的、在当前阶段实施的方案。

**工作原理**:
1.  **后台请求**: 在扩展的内容脚本中，使用标准的 `fetch` API 向"Files changed"和"Commits"标签页的 URL 发起 GET 请求。由于请求源于 `github.com`，它会自动附带用户的会话 Cookie，从而能获取到登录后才能看到的内容。
2.  **内存解析**: `fetch` 返回的是页面完整的 HTML 文本。接着，使用浏览器内置的 `DOMParser` API 将此文本解析为一个内存中的 `Document` 对象。
3.  **数据提取**: 最后，像操作普通 DOM 一样，使用 `querySelectorAll` 等方法在这个内存 `Document` 对象上查询并提取所需的数据。

**优点**:
- **用户无感知**: 整个过程在后台静默完成，对用户完全透明，提供了最佳体验。
- **高效标准**: 相比其他方案，此方法开销小、速度快，且完全基于浏览器标准 API。
- **实现简单**: 无需改动后端，也无需处理复杂的认证流程。

### 已排除方案
- **`iframe` 嵌入**: 不可行。GitHub 使用 `X-Frame-Options` 和 `Content-Security-Policy` 安全策略，禁止其页面被嵌入到 `iframe` 中。
- **后台新窗口**: 体验不佳。可能会有窗口闪烁问题，且实现更复杂。

## 3. 方案分析：后端 API 集成 (Analysis: Backend API Integration)

该方案由我们的后端服务通过 GitHub 官方 API 获取数据。

### 认证方式
- **OAuth 2.0 (标准方案)**: 行业标准的授权流程，用户通过 GitHub 授权页面给我们应用授予权限。
  - **资质要求**: 我们**不需要**任何特殊的公司或域名资质。只需在 GitHub 上注册一个 OAuth App，并利用 `chrome.identity` API 提供的扩展特定回调 URL，即可在没有外部服务器的情况下完成整个授权流程。
- **个人访问令牌 (PAT)**: 让用户手动创建并提供 PAT。此方案因用户体验差、安全风险高，不作为主要推荐。

## 4. 综合评估与最终建议 (Comparative Assessment & Final Recommendation)

| 评估维度 | 前端方案 (后台 Fetch & Parse) | 后端方案 (OAuth + API) |
| :--- | :--- | :--- |
| **可靠性** | 🟡 中等 | ✅ 高 |
| **实现复杂度** | ✅ 低 | 🔴 高 |
| **用户体验** | ✅ 最佳 (零配置) | 🟡 良好 (需一次性授权) |
| **维护成本** | 🔴 高 (依赖 DOM) | ✅ 低 (依赖稳定 API) |

### 最终建议
我们决定采纳**前端"后台 `fetch` 与 `DOMParser`"方案**。

### 核心理由
1.  **遵循既定原则**: `docs/github-token-extraction-analysis.md` 中已明确项目应"**重构为 DOM 解析为主的方案**"，以避免认证复杂性。本决策是该原则的延续。
2.  **速度与成本**: 此方案能以最低的开发成本和最快的速度交付价值，同时规避了复杂的后端开发和安全工作。
3.  **无缝用户体验**: "即装即用"的零配置体验是浏览器扩展成功的关键因素。

## 5. 风险管理与未来规划 (Risk Management & Future Outlook)

### 主要风险与缓解措施
- **风险**: 前端方案的最大风险在于其对 GitHub DOM 结构的依赖。GitHub 的前端改版可能导致我们的解析逻辑失效。
- **缓解措施**:
  - **编写健壮的选择器**: 采用更稳定的属性（如 `data-testid`）而非易变的 `class`。
  - **建立错误处理与监控**: 当解析失败时，向用户提供清晰的提示，并将错误上报，以便我们能快速响应。

### 未来展望
后端 API 方案将作为项目的**长期演进方向**。当未来出现无法通过 DOM 解析实现的功能时，我们再投入资源建设完整的后端 API 集成和 OAuth 认证体系。
